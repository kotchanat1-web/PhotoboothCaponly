## 1. เป้าหมาย — ระบบนี้แก้ปัญหาอะไร

ตู้ถ่ายรูปที่ใช้กล้อง DSLR เลือกกรอบ ถ่ายหลายช็อต เลือกฟิลเตอร์ พิมพ์รูปทันที และสแกน QR เพื่อดาวน์โหลดรูป / วิดีโอ / GIF
ใช้งานได้ 2 โหมด (DEC-005):
- **Kiosk** — ตู้ตั้งอยู่กับที่ ลูกค้าบริการตัวเอง จ่ายเงินผ่าน PromptPay QR หรือคูปอง
- **Event** — นำไปออกงานอีเวนต์ *(รายละเอียดดูหัวข้อ 3.1 MODE)*

**เป้าหมายของการทำใหม่** (จาก v1.0)
1. เป็นเจ้าของโค้ดเองทั้งหมด (ไม่พึ่ง binary / update server ของผู้ขาย)
2. ฟีเจอร์เทียบเท่าระบบเดิมที่ใช้งานจริง
3. เสถียรกว่าเดิม: กล้องหาย, ปริ้นเตอร์ไม่พร้อม, เน็ตหลุด ต้องกู้คืนเองได้
4. ตั้งค่า / เพิ่มกรอบ / ดูยอดขายได้ง่ายโดยไม่ต้องแก้ไฟล์ด้วยมือ
5. รองรับกล้อง Canon, Nikon, Fuji (DEC-004)

**ตัวเลขการใช้งานจริงจากระบบเดิม** (`photobooth.db`, ธ.ค. 2025 – พ.ย. 2026)
- 1,060 transactions, 7,940 ไฟล์
- ~91% จ่าย PromptPay 130 บาท / 1 ใบ; มีซื้อ 2 ใบ 250, 3 ใบ 375, 4 ใบ 500 บาท
- ~53 รายการเป็นคูปอง/ฟรี
- จอ 1920×1080 แนวนอน, กล้อง Canon EOS 70D, ปริ้นเตอร์ DNP DS-RX1 (4×6 นิ้ว, 600 dpi)

## 2. ผู้ใช้ — ใครใช้ ใช้ทำอะไร

| ผู้ใช้ | ต้องการ |
|---|---|
| ลูกค้า | ใช้ง่าย จ่ายเร็ว ถ่ายสวย ได้รูปทันที ดาวน์โหลดได้ |
| เจ้าของตู้ / แอดมิน | ตั้งราคา, เพิ่ม/ซ่อนกรอบ, ตั้งค่ากล้อง/ฟิลเตอร์, ดูยอดขาย, ดูสถานะตู้จากระยะไกล, ออกคูปอง, สลับโหมด Event/Kiosk |
| ช่างดูแล | รู้ทันทีเมื่อกล้อง/ปริ้นเตอร์/กระดาษมีปัญหา, ดู log ได้ |

## 4. 🔒 Business rules ที่ล็อกไว้

> **ยังไม่มีข้อใดถูกล็อก** — ด้านล่างเป็น *ร่างเสนอ* จาก AI รอ User อนุมัติทีละข้อ (RULES หัวข้อ 8) เมื่ออนุมัติแล้วจะย้ายขึ้นเป็น 🔒

ร่างเสนอ:
- BR-01 (เสนอ): ห้ามให้ลูกค้าจ่ายเงิน ถ้ากล้องหรือปริ้นเตอร์ไม่พร้อม (CAM-8, PRN-5)
- BR-02 (เสนอ): ทุกการจ่ายที่สำเร็จ ต้องได้ถ่าย/พิมพ์ หรือมีบันทึกให้ชดเชยได้ (archive หัวข้อ 5)
- BR-03 (เสนอ): จำนวนใบที่พิมพ์ = print_qty ที่จ่าย (PRN-4)
- BR-04 (เสนอ): ทุก transaction มี UUID ไม่ซ้ำ และ reconcile กับ server (PAY-7)
- BR-05 (เสนอ): ตารางราคาตั้งค่าได้ ไม่ฝังในโค้ด ค่าเริ่มต้น 1=130, 2=250, 3=375, 4=500 บาท (PAY-1)
- BR-06 (เสนอ): Template ID ต้องไม่ซ้ำ (TPL-6)
- BR-07 (เสนอ): การยืนยันการจ่ายเงินต้องมาจาก webhook ที่ตรวจ signature แล้วเท่านั้น ห้ามเชื่อผลจากฝั่งตู้/หน้าจอ (archive หัวข้อ 5 Security)

## 5. Flow การใช้งานหลัก

**State machine หลัก** (จาก v1.0 หัวข้อ 7 + โหมด)
```
Idle → CheckDevices
     → [kiosk] SelectPayment → (SelectQty → WaitPayment | EnterCoupon) → Paid
     → [event] (ข้ามการจ่ายเงิน — รายละเอียด MODE-3 รอ User ยืนยัน)
→ SelectTemplate → Instruction
→ Capture[1..N] (Countdown → Shoot → Review/Retake)
→ SelectFilter → Compose → Print → Export/Upload → ShowQR → Idle
```
ทุก state มี timeout และ error transition ไปหน้า "ขออภัย กรุณาติดต่อเจ้าหน้าที่" พร้อมบันทึกเหตุผล
Flow ละเอียดของระบบเดิม: archive หัวข้อ 2.2

## 6. Data model (ตาราง / ฟิลด์หลัก)

**Schema เดิม (อ้างอิง — ยังไม่ใช่ schema ใหม่)**
- `payment_transaction`: transaction_id_local, transaction_id_server, transaction_uuid, booth_id, print_qty, payment_price, payment_type_id, print_mode_id, source_id, event_id, camera_id, capture_count, charge_time, end_time, force_upload, upload_status, update_uuid
- `session_file`: file_id_local, transaction_id_local, file_uuid, file_type_id, file_path, create_time, upload_time, file_id_server
- `cash`, `cash_receive`: เงินสด (ไม่เคยใช้)
- payment_type_id: 4 = PromptPay, 1 = Coupon *(อนุมาน)*, 0 = ทดสอบ *(อนุมาน)*, 8 = Cash

**Schema ใหม่**: ยังไม่ออกแบบ — ต้องเสนอแผน + migration ให้ User อนุมัติก่อน (RULES หัวข้อ 9)

**ไฟล์ต่อ session**: `<sessionId>/captures/NN.jpg`, `captures_canceled/`, `-print4x6.jpg | -print2x6.jpg`, `-video.mp4`, `-gif.mp4`
**Template**: รูปแบบ `template.xml` เดิม (archive หัวข้อ 2.4)

## 7. Glossary

| คำ | ความหมาย |
|---|---|
| Kiosk mode | ตู้ตั้งอยู่กับที่ ลูกค้าบริการตัวเอง จ่ายเงินก่อนถ่าย |
| Event mode | ตู้ออกงานอีเวนต์ ผูกกับ event_id (รายละเอียดการจ่ายเงินรอ User ยืนยัน) |
| Session | การใช้งาน 1 รอบของลูกค้า 1 กลุ่ม, id = yyyyMMddHHmmss |
| Transaction | รายการชำระเงิน/คูปอง 1 รายการ ผูกกับ session |
| Template / กรอบ | layout รูปที่พิมพ์ (4×6 หรือ 2×6) มีช่องรูป + overlay |
| Shot / ช็อต | การถ่าย 1 ครั้ง = 1 ช่องในกรอบ |
| Driver | โมดูลที่คุยกับฮาร์ดแวร์จริงหรือจำลอง (camera/printer/payment/relay) |
| Mock | ไดรเวอร์จำลอง ใช้พัฒนา/ทดสอบโดยไม่ต้องมีฮาร์ดแวร์ หรือบัญชีจริง |
| Provider | ผู้ให้บริการ payment gateway (เช่น Omise) |

## 9. ข้อจำกัดที่รู้แล้ว

- เครื่อง Mac ที่ใช้พัฒนายังไม่มี Node.js และ Xcode Command Line Tools — ใช้ git ไม่ได้ (ISS-001)
- ทดสอบกล้อง DSLR จริง, ปริ้นเตอร์ DNP, บอร์ดรีเลย์ และ payment จริง บน Mac ไม่ได้ — ต้องทดสอบบนตู้ Windows โดย User
- SDK ของกล้องแต่ละยี่ห้ออาจต้องสมัครนักพัฒนากับผู้ผลิต และความสามารถบน Windows ต่างกัน *(อนุมาน — ต้องตรวจสอบเอกสารจริง)*
- Omise ต้องมีบัญชี merchant; การทดสอบใช้ test key ที่ User เป็นคนใส่ใน config แยก (ไม่อยู่ในโค้ด — RULES หัวข้อ 9)

### คำถามเปิด (จาก v1.0 หัวข้อ 9 — สถานะล่าสุด)
1. ~~เทคโนโลยี~~ → ตัดสินแล้ว DEC-003
2. ~~Payment gateway~~ → ตัดสินแล้ว DEC-006
3. Backend + storage: ทำเอง (Supabase/Firebase/Cloudflare R2) หรือ self-host? — **ยังไม่ตัดสินใจ**
4. จำนวนตู้ — 1 ตู้ หรือหลายตู้? — **ยังไม่ตัดสินใจ**
5. ย้ายข้อมูล transaction เก่า (1,060 รายการ) ไหม? — **ยังไม่ตัดสินใจ**
6. หน้าจอ: แนวนอน 1920×1080 หรือแนวตั้ง? — **ยังไม่ตัดสินใจ** (NFR: รองรับทั้งสองแบบ)
7. จำนวนช็อต = จำนวนช่องในกรอบเสมอ หรือถ่ายเกินแล้วเลือก? — **ยังไม่ตัดสินใจ**
8. (ใหม่) รายละเอียดโหมด Event: จ่ายเงินไหม / จำกัดใบไหม / ไม่มีรีเลย์ได้ไหม — **ยังไม่ตัดสินใจ**
9. (ใหม่) SDK/ไลบรารีต่อยี่ห้อกล้อง — **ต้องตรวจสอบ** ก่อนเสนอ DEC

## Non-Functional Requirements (จาก v1.0 หัวข้อ 5 — ไม่เปลี่ยน)

| หัวข้อ | เป้าหมาย |
|---|---|
| ความเร็ว | จ่ายเงินสำเร็จ → เริ่ม live view < 5 วินาที; ถ่ายเสร็จ → เริ่มพิมพ์ < 15 วินาที; 1 รอบ ≤ 3 นาที |
| ความเสถียร | ทำงานต่อเนื่อง 16 ชม./วัน; crash แล้ว watchdog เปิดใหม่และกู้ session ที่จ่ายแล้วได้ |
| เงินลูกค้า | ทุกการจ่ายที่สำเร็จต้องได้ถ่าย/พิมพ์ หรือมีบันทึกให้ชดเชยได้ |
| Offline | ถ่าย/พิมพ์ได้แม้เน็ตหลุด (ยกเว้นการจ่าย QR) — sync ทีหลัง |
| Logging | structured log (JSON), หมุนไฟล์รายวัน, ลบ > 30 วัน, ไม่ log ข้อมูลส่วนตัว |
| Security | API key/secret ไม่ฝังใน binary แบบ plain; payment callback ตรวจ signature; HTTPS ทั้งหมด |
| เวลา | ซิงค์ NTP ตอนเปิด |
| ความละเอียดจอ | 1920×1080 แนวนอน + แนวตั้ง, DPI scaling |
