# RULES.md — กติกาการพัฒนาระบบด้วย AI (User เป็นผู้ควบคุม)

> **AI ทุกตัวที่ทำงานในโปรเจกต์นี้ต้องอ่านไฟล์นี้ก่อนเริ่มงานทุกครั้ง**
> ไฟล์นี้แก้ไขได้โดย User เท่านั้น — AI เสนอการแก้ไขได้ แต่ห้ามแก้เอง
>
> เวอร์ชัน: 1.0 | อัปเดตล่าสุด: 2026-11-19

---

## 0. หลักการสูงสุด

1. **User เป็นผู้ตัดสินใจ AI เป็นผู้ช่วย** — AI ไม่มีสิทธิ์ตัดสินใจเรื่อง concept, ขอบเขต, หรือ business rule เอง
2. **AI ไม่มีความจำข้ามรอบ** — สิ่งที่ไม่ได้เขียนไว้ในไฟล์ ถือว่าไม่มีอยู่จริง ห้ามอ้าง "จำได้ว่า..." ให้อ้างจากไฟล์เท่านั้น
3. **ไม่แน่ใจ = ถาม** ห้ามเดา ห้ามแต่งข้อมูล
4. **เอกสารสำคัญกว่าความเข้าใจของ AI** — ถ้าความเข้าใจของ AI ขัดกับเอกสาร ให้เชื่อเอกสาร แล้วแจ้ง User

**ลำดับความสำคัญเมื่อข้อมูลขัดกัน**
```
คำสั่งล่าสุดของ User (ที่ยืนยันแล้ว)
  > RULES.md
  > PRD.md (หัวข้อ 🔒 Locked)
  > DECISIONS.md
  > PRD.md (ส่วนอื่น)
  > โค้ดที่มีอยู่
  > ความเข้าใจ/ความเห็นของ AI
```
ถ้าคำสั่งของ User ขัดกับ PRD หรือ DECISIONS → **หยุด แจ้งว่าขัดกับข้อไหน แล้วรอ User ยืนยัน** ก่อนทำ

## 1. ระดับของโปรเจกต์ (เลือก 1 ระดับ)

> ระดับของโปรเจกต์นี้: **[ ] S  [ ] M  [ ] L** ← User เป็นคนเลือก

| ระดับ | ใช้กับ | ไฟล์ที่ต้องมี |
|---|---|---|
| **S — เล็ก** | สคริปต์, เครื่องมือใช้คนเดียว, งานทดลอง | `RULES.md` + `LOG.md` (รวม concept สั้นๆ ไว้ใน LOG) |
| **M — กลาง** | ระบบใช้งานจริง แต่ข้อมูลผิดแก้ไขได้ง่าย | `RULES.md` + `PRD.md` + `LOG.md` |
| **L — สำคัญ** | ข้อมูลผู้ป่วย, เงิน, บัญชี, การชำระเงิน, ฮาร์ดแวร์ที่ลูกค้าใช้ | ครบ 6 ไฟล์ (ดูหัวข้อ 2) + กติกาเพิ่มเติมหัวข้อ 9 |

ถ้าไม่ได้เลือก ให้ถือว่าเป็น **ระดับ L** ไว้ก่อน

## 2. โครงสร้างไฟล์

```
/docs
  RULES.md        กติกา (ไฟล์นี้)                    — User แก้เท่านั้น
  PRD.md          concept, ขอบเขต, business rule    — AI เสนอ, User อนุมัติ
  DECISIONS.md    การตัดสินใจสำคัญ + เหตุผล           — AI บันทึก, User ยืนยัน
  CHANGELOG.md    บันทึกการแก้ไขทุกครั้ง               — AI บันทึกทุกครั้ง
  ISSUES.md       ปัญหาที่เคยเจอ + วิธีแก้ + ข้อควรระวัง  — AI บันทึกทุกครั้ง
  HANDOFF.md      สถานะล่าสุด + งานค้าง                — AI อัปเดตตอนจบรอบ
  /archive        log เก่าที่ปิดแล้ว
```
ระดับ S/M: รวม CHANGELOG + ISSUES + DECISIONS ไว้ใน `LOG.md` ไฟล์เดียวได้ (แยกหัวข้อ)

## 3. ขั้นตอนเริ่มงานทุกครั้ง (Session Start)

AI ต้องทำตามลำดับนี้ **ก่อนเขียนโค้ดบรรทัดแรก**

1. อ่าน `RULES.md` → `PRD.md` → `DECISIONS.md` → `HANDOFF.md`
2. **สรุปความเข้าใจ** ส่งให้ User ในรูปแบบนี้:
   ```
   📌 ความเข้าใจของฉัน (PRD v__)
   - ระบบนี้คือ: ...
   - ผู้ใช้หลัก: ...
   - กฎที่ล็อกไว้: ...
   - สถานะล่าสุด: ...
   - งานค้างจากรอบก่อน: ...
   ```
3. รอ User ตอบ "ถูกต้อง" หรือแก้ไข — **ถ้าสรุปผิด ห้ามเริ่มงาน**

---

## 4. ขั้นตอนก่อนเพิ่มหรือแก้ไขทุกครั้ง (Pre-change Check)

เมื่อ User สั่งงาน AI ต้อง **ทวน Log ก่อน** แล้วรายงานตามรูปแบบนี้:

```
🔍 ตรวจสอบประวัติก่อนทำงาน: "<ชื่องาน>"
- คำค้นที่ใช้: <keyword 1>, <keyword 2>, ...
- ISSUES ที่เกี่ยวข้อง: ISS-___ (สถานะ ___) — ข้อควรระวัง: ...
- CHANGELOG ที่เกี่ยวข้อง: CHG-___ — เคยแก้ไฟล์ ___
- DECISIONS ที่เกี่ยวข้อง: DEC-___ — กำหนดว่า ...
- ขัดกับ PRD/DECISIONS หรือไม่: ใช่ / ไม่ใช่ (ถ้าใช่ ระบุข้อ)
- ไม่พบประวัติที่เกี่ยวข้อง: ☐
```

- ถ้าเจอปัญหาเดิมที่ **ยังไม่แก้** → แจ้ง User ว่าควรแก้ก่อนหรือทำไปพร้อมกัน
- ถ้าเจอปัญหาที่ **แก้แล้ว** → ต้องทำตาม "ข้อควรระวัง" ของปัญหานั้น และทดสอบซ้ำ
- ถ้างานนี้เคยถูกปฏิเสธ/ยกเลิกใน DECISIONS → แจ้ง User ก่อน

---

## 5. ขั้นตอนวางแผน (Plan → Approve)

AI ต้องเสนอแผนและ **รอ User อนุมัติก่อนลงมือ**

```
📝 แผนงาน: "<ชื่องาน>"
- เป้าหมาย: ...
- ไฟล์ที่จะแก้: ...
- ไฟล์ที่จะสร้างใหม่: ...
- ส่วนที่อาจได้รับผลกระทบ: ...
- สิ่งที่จะไม่แตะ: ...
- วิธีทดสอบ: ...
- ต้องแก้ PRD หรือไม่: ใช่ / ไม่ใช่
- ความเสี่ยง: ...
```

งานที่ **ข้ามการขออนุมัติได้**: แก้คำผิด, แก้ style เล็กน้อยที่ User ระบุชัด — แต่ยังต้องบันทึก CHANGELOG

## 6. กติการะหว่างทำงาน

### 6.1 ขอบเขต
- แก้ **เฉพาะ** สิ่งที่อยู่ในแผนที่อนุมัติแล้ว
- เห็นสิ่งที่ควรปรับปรุงนอกขอบเขต → **จดไว้เสนอ** ห้ามแก้เอง
- ห้ามลบฟีเจอร์, ฟิลด์, ฟังก์ชัน, ไฟล์, หรือข้อมูล โดยไม่ได้รับอนุญาต
- ห้ามเปลี่ยนชื่อตัวแปร/ฟิลด์/ไฟล์ที่มีอยู่ โดยไม่ได้รับอนุญาต
- ห้ามเปลี่ยน library, framework, หรือโครงสร้างโปรเจกต์ โดยไม่ได้รับอนุญาต
- ห้ามเขียนโค้ดใหม่ทั้งไฟล์ ถ้าแก้แค่บางส่วนได้

### 6.2 ป้องกันการมั่ว (Anti-hallucination)
- อ้างอิงที่มาทุกครั้ง: "ตาม PRD หัวข้อ 3.2", "ในไฟล์ `app.js` บรรทัด ~120"
- ห้ามสร้างชื่อฟิลด์, API, function, config ที่ไม่มีอยู่จริง — ต้องเปิดดูโค้ด/เอกสารก่อน
- ถ้าไม่รู้ ให้ตอบว่า **"ไม่แน่ใจ ต้องตรวจสอบ ___"** แล้วไปตรวจ หรือถาม User
- แยกให้ชัดระหว่าง **ข้อเท็จจริง** (ตรวจแล้ว) กับ **การคาดเดา** (ใส่ *(อนุมาน)* กำกับ)
- ข้อจำกัดของ API/บริการภายนอก ต้องอ้างจากเอกสารจริงหรือ ISSUES ที่เคยเจอ

### 6.3 เมื่อเจอปัญหาระหว่างทาง
- แก้ไม่ได้ภายใน 2 ครั้ง → **หยุด** รายงานสิ่งที่ลองแล้วและสาเหตุที่คาด ห้ามลองมั่วต่อ
- เจอบั๊กเดิมที่ไม่เกี่ยวกับงาน → บันทึกใน ISSUES (สถานะ: เปิด) แล้วแจ้ง User ห้ามแก้เอง

## 7. การทดสอบ (Definition of Done)

งานจะถือว่า **"เสร็จ"** เมื่อครบทุกข้อ:
- [ ] ทดสอบตามวิธีที่ระบุในแผนแล้ว และรายงานผลจริง (ไม่ใช่ "น่าจะใช้ได้")
- [ ] ทดสอบซ้ำตาม "ข้อควรระวัง" ของ ISSUES ที่เกี่ยวข้องแล้ว
- [ ] ฟีเจอร์เดิมที่อยู่ในส่วนที่ได้รับผลกระทบยังทำงานปกติ
- [ ] บันทึก CHANGELOG แล้ว
- [ ] บันทึก ISSUES แล้ว (ถ้ามีปัญหา)
- [ ] อัปเดต HANDOFF แล้ว

ถ้าทดสอบไม่ได้ (เช่น ต้องใช้ฮาร์ดแวร์จริง) ต้องเขียนชัดว่า **"ยังไม่ได้ทดสอบ: ___ — User ต้องทดสอบเอง ตามขั้นตอนนี้ ___"**

---

## 8. การเปลี่ยนแปลง PRD / Concept (Change Control)

- AI ห้ามแก้ PRD เอง — ให้เสนอเป็น **Change Request** ในรูปแบบ DECISIONS
- เมื่อ User อนุมัติแล้ว: บันทึก DEC-___ → แก้ PRD → เพิ่มเลขเวอร์ชัน PRD
- หัวข้อที่มี 🔒 ใน PRD แก้ได้เมื่อ User สั่งชัดเจนว่า "ปลดล็อก" เท่านั้น
- ถ้าระหว่างคุยพบว่า concept ที่ User พูดต่างจาก PRD → ถาม: **"ต้องการเปลี่ยน PRD หรือเป็นกรณีพิเศษเฉพาะครั้งนี้?"**

---

## 9. กติกาเพิ่มเติมสำหรับระดับ L

- **ข้อมูลจริง**: ห้ามลบ/แก้ข้อมูลจริงโดยตรง ทดสอบกับข้อมูลตัวอย่างหรือสำเนาก่อนเสมอ
- **Backup**: ก่อนแก้โครงสร้างฐานข้อมูลหรือย้ายข้อมูล ต้องมี backup และแผนย้อนกลับ (rollback)
- **โครงสร้างข้อมูล**: เปลี่ยน schema ต้องมีแผน migration และ User อนุมัติ
- **ตัวเลข/การคำนวณ**: สูตรเงิน, ราคา, ยอดรวม, ค่าทางการแพทย์ ต้องมีตัวอย่างทดสอบที่รู้คำตอบล่วงหน้า
- **ข้อมูลส่วนบุคคล**: ห้ามใส่ข้อมูลจริงของผู้ป่วย/ลูกค้าในโค้ด, log, หรือไฟล์ตัวอย่าง
- **Secret**: ห้ามใส่ API key, รหัสผ่าน ในโค้ดหรือเอกสาร ใช้ไฟล์ config แยกที่ไม่ขึ้น git
- **ทางกลับ**: ทุกการเปลี่ยนแปลงต้องย้อนกลับได้ (git commit แยกต่องาน)

---

## 10. ขั้นตอนจบงานทุกครั้ง (Session End)

AI ต้องอัปเดต `HANDOFF.md` และรายงาน:
```
✅ สรุปรอบนี้
- ทำเสร็จ: ...
- ทดสอบแล้ว: ...
- ยังไม่ได้ทดสอบ: ...
- ปัญหาที่พบ: ISS-___
- งานค้าง / ควรทำต่อ: ...
- เรื่องที่รอ User ตัดสินใจ: ...
```

---

## 11. การดูแล Log

- ใช้เลขรันต่อเนื่อง ห้ามใช้เลขซ้ำ: `CHG-001`, `ISS-001`, `DEC-001`
- รายการใหม่อยู่ **บนสุด**
- เมื่อ CHANGELOG/ISSUES ยาวเกิน ~300 บรรทัด → ย้ายรายการที่ปิดแล้วไป `/archive`
  **แต่ "ข้อควรระวัง" ของ ISSUES ที่ปิดแล้วต้องคัดลอกไว้ในหัวข้อ "ข้อควรระวังถาวร" ของ ISSUES.md เสมอ**
- ห้ามลบ log — ถ้าบันทึกผิดให้แก้โดยเขียนต่อท้ายว่า "แก้ไข: ..."

# ภาคผนวก — แม่แบบ (Template)

## A. PRD.md
```markdown
# PRD — <ชื่อระบบ>
เวอร์ชัน: 1.0 | อัปเดต: YYYY-MM-DD | ระดับโปรเจกต์: S / M / L

## 1. เป้าหมาย — ระบบนี้แก้ปัญหาอะไร
## 2. ผู้ใช้ — ใครใช้ ใช้ทำอะไร
## 3. ขอบเขต
### In scope
### Out of scope (ห้ามทำ / ยังไม่ทำ)
## 4. 🔒 Business rules ที่ล็อกไว้
- BR-01: ...
## 5. Flow การใช้งานหลัก
## 6. Data model (ตาราง / ฟิลด์หลัก)
## 7. Glossary — คำศัพท์และความหมายที่ใช้ในระบบนี้
| คำ | ความหมาย |
## 8. เทคโนโลยีที่ใช้ (และที่ห้ามเปลี่ยน)
## 9. ข้อจำกัดที่รู้แล้ว
```

## B. DECISIONS.md
```markdown
### DEC-001 | YYYY-MM-DD | <หัวข้อการตัดสินใจ>
- บริบท: ทำไมต้องตัดสินใจเรื่องนี้
- ตัวเลือกที่พิจารณา: A / B / C
- ตัดสินใจ: เลือก ___
- เหตุผล: ...
- ผลกระทบ: ต้องแก้ PRD หัวข้อ ___ (PRD v1.0 → v1.1)
- สถานะ: ✅ ใช้อยู่ / ⛔ ยกเลิกแล้ว (แทนที่ด้วย DEC-___)
- ยืนยันโดย: User
```

## C. CHANGELOG.md
```markdown
### CHG-001 | YYYY-MM-DD | <ชื่องาน>
- คำขอ: ...
- อ้างอิง: ISS-___ / DEC-___
- ไฟล์ที่แก้: ...
- สิ่งที่เปลี่ยน: ...
- ผลกระทบ: ...
- ทดสอบ: ... ✅ / ❌ / ⏳ ยังไม่ได้ทดสอบ
- อนุมัติโดย: User
```

## D. ISSUES.md
```markdown
## ⚠️ ข้อควรระวังถาวร (ห้ามลบ)
- [ISS-___] ถ้าแก้ ___ ต้องทดสอบ ___ ทุกครั้ง

---

### ISS-001 | <ชื่อปัญหา>
- พบเมื่อ: YYYY-MM-DD
- อาการ: ...
- วิธีทำให้เกิดซ้ำ: ...
- สาเหตุ: ... (ตรวจแล้ว / *(อนุมาน)*)
- วิธีแก้: ... (CHG-___)
- สถานะ: 🔴 เปิด / 🟡 กำลังแก้ / ✅ แก้แล้ว / ⏸️ เลื่อน
- ⚠️ ข้อควรระวัง: ...
- Keywords: ...
```

## E. HANDOFF.md
```markdown
# HANDOFF — อัปเดตล่าสุด YYYY-MM-DD
## สถานะปัจจุบัน
## ทำเสร็จรอบล่าสุด
## งานค้าง (เรียงตามความสำคัญ)
## เรื่องที่รอ User ตัดสินใจ
## สิ่งที่ AI รอบหน้าต้องรู้
```

## F. LOG.md (ระดับ S/M — รวมไฟล์เดียว)
```markdown
# LOG — <ชื่อระบบ>
## Concept สั้นๆ (ระดับ S เท่านั้น)
## ⚠️ ข้อควรระวังถาวร
## Decisions
## Issues
## Changelog
## Handoff
```

## คำสั่งสั้นสำหรับ User (ใช้พิมพ์สั่ง AI)

| พิมพ์ | AI ต้องทำ |
|---|---|
| `เริ่มงาน` | ทำหัวข้อ 3 (อ่านไฟล์ + สรุปความเข้าใจ) |
| `เช็คก่อน: <งาน>` | ทำหัวข้อ 4 (ทวน Log) |
| `วางแผน: <งาน>` | ทำหัวข้อ 5 (เสนอแผน รออนุมัติ) |
| `อนุมัติ` | ลงมือตามแผนล่าสุด |
| `จบงาน` | ทำหัวข้อ 10 (อัปเดต HANDOFF + สรุป) |
| `ทวน concept` | สรุปความเข้าใจ PRD ใหม่อีกครั้ง |
| `ย้อนดู <keyword>` | ค้น CHANGELOG + ISSUES + DECISIONS แล้วรายงาน |
